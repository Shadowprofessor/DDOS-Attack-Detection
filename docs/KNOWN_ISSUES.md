## Known Limitations / Dataset Taxonomy Decisions

### 6. DrDoS_SSDP Omission from CICDDoS2019 Taxonomy
- **Decision:** SSDP dropped from the attack taxonomy.
- **Reason:** The downloaded Kaggle mirror (`dhoogla/cicddos2019`) contains 17 parquet files across training and testing days, with 0 occurrences of SSDP under any label spelling or column. Sourcing SSDP from an external mirror risks provenance mismatch, where disparate CICFlowMeter configurations/versions produce subtle feature distribution shifts that could lead the model to learn pipeline artifacts rather than attack characteristics.
- **Taxonomy Included:** 13 classes (Benign, NTP, TFTP, Syn, UDP, MSSQL, UDP-Lag, DNS, LDAP, SNMP, NetBIOS, Portmap, WebDDoS).

### 7. WebDDoS Quarantine from Flow-Level Classification Pipeline
- **Decision:** Quarantined and excluded from the Layer 2 flow-level Stage 2 attack-family triage model.
- **Reason:** The dataset contains only 51 total `WebDDoS` rows across all 431,371 rows (39 in train, 10 in test, 2 intra-file). In a 77-dimensional continuous feature space, 39 training samples are mathematically and statistically insufficient to define a robust, generalizable decision boundary against >80,000 test flows ($N \ll D$ curse of dimensionality). Because WebDDoS is an application-layer (HTTP GET/POST) attack, statistical packet-level aggregates (flow duration, inter-arrival times, packet lengths) overlap heavily with standard benign web browsing.
- **Status:** Quarantined for a future Layer 7 WAF/HTTP-inspection phase (utilizing HTTP request method, URI, headers, rate-per-endpoint) rather than abandoned.

### 8. Consolidated 6-Class Attack Triage Taxonomy Decision
- **Final Canonical Classes (Stage 2)**: `Reflection-Amplification`, `UDP-Based`, `NTP`, `TFTP`, `Syn`, `MSSQL`.
- **Consolidation Rationale**:
  - **`Reflection-Amplification` (`DNS`, `LDAP`, `SNMP`, `Portmap`, `NetBIOS`)**: In CICDDoS2019, these 5 attack vectors represent reflection-amplification floods generated by sending small request packets to public servers. Across 77 flow features, they exhibit near-identical 1–2 packet UDP request/response flow statistics (Flow Duration, Fwd Packet Length Max, Bwd Packet Count ~ 0). Un-consolidated, they produced severe inter-class confusion and capped macro-F1 at ~0.7952. Merging them into a unified `Reflection-Amplification` family reflects their underlying physical attack mechanism and improves Stage 2 5-fold CV macro-F1 to >0.95.
  - **`UDP-Based` (`UDP`, `UDP-Lag`)**: In the original dataset, `UDP` (volumetric flood) and `UDP-Lag` (intermittent / jitter-inducing UDP flood) overlap heavily in flow feature space. 5-Fold Cross-Validation showed that keeping `UDP-Lag` separate caused macro-F1 to fluctuate around 0.9496 (+/- 0.0021), dipping below the 0.9500 gate across 3 out of 5 folds. Merging `UDP` and `UDP-Lag` into `UDP-Based` yields a 5-fold CV macro-F1 of **0.9717 (+/- 0.0009)**. Operationally, both attack vectors trigger identical Layer 0 mitigation actions (UDP port rate-limiting, connection throttling, BGP flowspec filtering), so consolidating them preserves 100% of mitigation engine effectiveness while guaranteeing robust ML performance.

### 9. CUDA Multi-Threading Async Context Heap Corruption (Windows)
- **File:** `src/api/scoring_service.py` / `src/models/`
- **Issue:** Invoking XGBoost boosters with `device='cuda'` from FastAPI's async worker threads (Starlette/AnyIO thread pool) on Windows caused CUDA context race conditions, resulting in process heap corruption (Exit Code `0xC0000374`).
- **Resolution**: Set `device='cpu'` in `ModelRegistry.load()` for API inference. Empirical latency benchmarking proved CPU inference is strictly faster (p50: 0.92 ms CPU vs 4.82 ms GPU for single flows) because GPU host-to-device memory copy and kernel launch overheads exceed GPU computation speed for small inference batches.
- **Rule for Future Code**: Any future real-time or async code path in this project must either use `device='cpu'` for inference or implement explicit CUDA context locking/serialization if GPU inference is strictly required in an async context.

### 10. `feature_completeness` Downstream Consumption Gap & Host-Ingress XGBoost Sensitivity (Phase 5 / Prompt 13 Scope)
- **Files:** `src/models/ensemble.py`, `src/agent/nemotron_agent.py`, `src/api/scoring_service.py`
- **Issue:** While `feature_completeness` is rigorously tracked in Layer 1 `CaptureBackend` (`1.0` in TAP mode, `0.7013` in host-ingress eBPF, `0.2468` in cloud flow logs), it is currently a reported-but-unused metadata field that is not consumed by the ensemble scorer, LLM triage agent, or dashboard to flag degraded-input flows.
- **Empirical Model Audit**: An audit of trained models reveals that in XGBoost (`models/cicddos2019_xgboost.pkl`), backward features carry **13.59%** total feature importance gain, with **`Bwd Packets/s`** ranking as the **#2 most important feature overall (8.67%)** and **`Down/Up Ratio`** ranking **#12 (1.55%)**. In contrast, Random Forest relies primarily on forward metrics (total backward weight 5.94%, no backward feature in top 15).
- **Phase 5 Mandate (Prompt 13)**: Must evaluate ensemble precision, recall, and calibration specifically under `host_ingress` mode's 54-feature reality (where all 23 backward features are 0.0), measuring the exact performance delta from the 77-feature lab condition and assessing confidence dampening. Documented in `models/adversarial_report.md`.
