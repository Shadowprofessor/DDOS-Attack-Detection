# Purple-team lab (v4.6.0 safety layer · v4.6.1 measured lab runs · v5.1.0 four more scenarios)

**v4.6.0** shipped the safety layer, scenario catalogue and mock runner, sending no traffic. **v4.6.1**
(approved by the owner) adds a gated lab-only generator, a Mininet orchestrator, nftables containment,
and the first measured lab run, reported below as measured.

## Safety model (enforced in code: `lab/safety.py`)

| Control | Rule | Test (`tests/test_lab_safety.py`) |
|---|---|---|
| Scope file | `lab/lab_scope.yaml` is validated on load. Allowed networks must be IPv4 private ranges no larger than /16 and never loopback / link-local / multicast / reserved. Every host role must be inside them. | `TestScopeValidation` |
| Targets | Public IPv4/IPv6 (e.g. 8.8.8.8, 1.1.1.1, 2606:4700:4700::1111) refused; private-but-not-allowlisted (10.0.0.4, 192.168.1.10, fd00::1) refused; loopback, link-local, multicast and unspecified refused. | `TestTargets` |
| Caps | packets/s ≤ `max_pps` (2,000), duration ≤ `max_duration_s` (120 s), concurrent scenarios ≤ `max_concurrent` (1). | `TestCaps` |
| Kill switch | `lab/KILL` file, `DDOS_LAB_KILL=1`, or `KillSwitch.trip()` (signal hook). It is checked before start **and before every tick**, so a running scenario stops within one tick. | `test_kill_switch_stops_within_one_tick`, `test_tripped_switch_blocks_start` |
| Environment | Refuses unless **WSL2** (`/proc/version`) **and Mininet** (`mn` on PATH and an `hN-ethX` interface) are detected. CI therefore always gets the refusal path. | `test_refuses_outside_lab`, `test_runner_refuses_outside_lab_before_anything` |
| No traffic code | AST scan: nothing in `lab/` imports `scapy`, `socket`, `subprocess`, `requests`, `httpx`, `urllib`, `http`, `asyncio`, `ssl`, `ctypes`, `multiprocessing`, or calls `system`/`popen`/`exec*`/`send*`/`connect`. | `test_lab_package_contains_no_traffic_code` |

Planned for v4.6.1 (after approval): nftables **egress-drop** rules on the lab host, so anything from
the lab subnet toward a non-lab interface is dropped. A lab-only test (`@pytest.mark.lab`, skipped in
CI) proves a lab packet aimed at a real interface is dropped.

## Measured lab runs (`run2` v4.6.1, `run3` v5.1.0; both 2026-11-11)

**Setup.** WSL2 (kernel 6.18) running Mininet with Open vSwitch on one isolated LAN, `10.99.0.0/24`,
with no NAT and no route out. Each scenario's traffic is generated by `lab/traffic/generator.py`
inside its source host's namespace and captured on the victim's interface. The pcaps are then run
through the **real** stack (`src/eval/lab_analysis.py`):
- `FlowExtractor` builds CICFlowMeter flows;
- **L1** = threshold detector + signature filter + low-and-slow detector (as `/score/flow` calls them);
- **L2** = RF+XGB ensemble; **OOD** = supervised OOD detector;
- **L3** = rule-based analyst on the per-victim aggregate. No LLM is called.

L1 runs on every flow. L2/OOD run on an evenly spaced sample of ≤1,500 flows per scenario
(`ml_scored_flows` in `results.json`), because the 183 MB RF scores about 10 ms per flow.

**MTTD definition.** MTTD = (last packet of the first flagged flow) − (scenario start). This assumes
a flow is exported the instant its last packet is seen. A live CICFlowMeter-style exporter adds its

for a flow-based deployment.

### Findings (as measured; nothing tuned against this run)

1. **L2 (ML ensemble) did not recognise the lab SYN flood: 0 of 1,452 sampled flows flagged.**
   For the floods it flagged only 1–16% of sampled flows (mostly as UDP-Reflection-Amplification).
   Here a SYN flow is SYN → SYN-ACK → RST, because the lab sources are live hosts. That shape is
   unlike CIC-DDoS2019's. Together with v4.4.0, this is consistent evidence that the classifier
   does not transfer beyond its training capture. Detection here came from L1 rate/signature rules.
   **v5.1.0 investigation (no retraining; documented limitation).** All 1,452 scored flows were
   labelled `Benign`. The model has every feature it needs; the lab flows sit where the training data
   is almost all benign:

   | Feature (median) | Train `Syn` | Train `Benign` | Lab SYN flood |
   |---|---:|---:|---:|
   | Flow Duration (µs) | 39,759,940 | 20,685 | 16.9 |
   | Total Fwd / Bwd Packets | 10 / 0 | 2 / 2 | 2 / 1 |
   | SYN Flag Count | 0 | 0 | 2 |
   | Init Bwd Win Bytes | 0 | 0 | 42,340 |
   | Flow Packets/s | 0.33 | 192 | 177,224 |

   CIC-DDoS2019 `Syn` flows are long and mostly unanswered (65% have no backward packet). The lab's
   are 17 µs answered handshakes. In the training set, flows with that shape (answered, < 1 ms, ≤ 3
   forward packets, no payload) are **212 `Syn` vs 9,762 `Benign`**, about 46:1 benign. So `Benign`
   is the answer the training data supports. Retraining on CIC-DDoS2019 cannot change this. A fix
   needs labelled, lab-shaped SYN traffic that is independent of the evaluation run: training on
   `run2` would test on training data, and new traffic is out of scope for v5.1.0. It is listed as
   a limitation in `REPORT.md` §7.
2. **L1 false positives on legitimate traffic.** The rate thresholds fired on **41% of flash-crowd
   flows** and 3% of benign-baseline flows. A flash crowd is the case the platform must *not* alert
   on, and it would open an incident. Recommended fix: per-destination adaptive baselines (EWMA)
   instead of fixed thresholds. Then validate on a **fresh** lab run.
3. **The SYN flood was mislabelled by L3 ("HTTP flood" early, low-and-slow for the full run).**
   v5.1.0 found the cause in the lab aggregate builder (`src/eval/lab_analysis.py`). It counted
   **every** TCP flow to 80/443 as an HTTP request, including the 34,842 zero-payload handshakes
   (≈ 860 "HTTP rps" in the first 2 s), plus 126 long zero-byte flows as "slow connections". Now only
   flows that carried client bytes count as HTTP. That changes nothing for the HTTP scenarios: every
   HTTP flow in low-and-slow, flash crowd and benign baseline carries payload. The test is
   `test_zero_payload_handshakes_to_443_are_not_http`.
   **Measured after the fix: L3 does not detect the SYN flood** ("Benign / insufficient evidence").
   The SYN-flag ratio is 0.667, under the rule's 0.7, because every SYN is answered by a SYN-ACK
   (SYN, SYN-ACK, RST = 2/3). The threshold was **not** retuned against this run. That needs a
   fresh run to validate it. A wrong name became an honest miss. The production
   `LowSlowDetector` still counts zero-byte flows ≥ 10 s as slow; handshake-aware counting is future
   work.
4. **DNS reflection was reported as generic UDP reflection/amplification.** The rule looks for
   reflector ports among *destination* ports, but reflected traffic arrives *from* port 53/123.
   NTP still mapped correctly because its family is the generic one. Recommended fix: use source
   ports for the reflector check.
5. **Novel/OOD mix was only partially detected.** OOD flagged 48% of sampled flows (704 of 1,480)
   and L3 found no named pattern.
6. **Bug found and fixed in the product.** `family_from_text()` matched "ood" inside "fl**ood**", so
   every "UDP flood" analysis was filed under the zero-day playbook. It now uses whole-word
   matching, with a regression test (`tests/test_ir.py`).
7. **Containment proven.** With a NAT path deliberately opened, 3/3 probes to TEST-NET-1 reached
   the lab boundary and were dropped by nftables; 0 appeared on `eth0`. `run3` repeated it with the
   same result.

**v5.1.0 scenarios (`run3`), as measured.** "Not detected" means that layer never fired.
8. **ICMP flood: detected by L1 and L3.**
   - L1 flagged 20/20 flows; L3 named it "ICMP flood".
   - **L2: not detected** (0/20, all `Benign`). **OOD: not detected** (0/20).
   - The 85,268 echo requests collapse into 20 long flows, one per source. A flow is only judged
     when its last packet is seen, so the 55.8 s MTTD is bound by the scenario length, not the
     detector. A live exporter's active timeout would cut it short.
9. **TCP ACK flood: partial (L1 only).**
   - L1 flagged 31,276/31,278 flows. L2 flagged 1,486/1,490 sampled flows, but labelled them
     `UDP-Reflection-Amplification`, the wrong family. OOD flagged 1,066/1,490.
   - **L3: not detected.** The rule analyst has no ACK-flood rule. Before the aggregate fix it said
     "Slowloris", for the same zero-byte reason as finding 3.
   - MTTD 1.2 s.
10. **TCP RST flood: partial (L1 only).**
    - L1 flagged 59,259/59,263 flows. L2 flagged only 13/1,482 sampled flows; OOD 1/1,482.
    - **L3: not detected.**
    - MTTD 1.5 s.
11. **LAND attack: partial.** All 17,999 packets share one 5-tuple (src = dst, sport = dport), so
    the capture holds **one flow**.
    - L1, L2 (`Syn`) and OOD all flagged that one flow.
    - L3 called it "TCP SYN flood". LAND does use SYNs, but there is no LAND rule, so the family is
      wrong for this scenario.
    - MTTD 60.8 s, bound by the single flow ending with the scenario (same caveat as ICMP). One flow
      is too small a sample to claim L2 or OOD "detect LAND".

**Analysis-harness corrections made before these numbers** (each committed separately):
1. aggregate built from both directions (victim replies looked like carpet-bombing);
2. low-and-slow detector missing from L1;
3. ports read from CICFlowMeter features, which have none.
The first pass is kept in `data/lab_runs/run2/analysis_v1_results.json` (gitignored).

## v5.3.0: DEV vs HELD-OUT (run4)

**Protocol.**
- Detection rules, thresholds and the L2 recipe were set on **DEV = runs 2+3** only.
- **run4** (fresh seed 4004, the same 12 canonical scenarios) was recorded *before* tuning and analysed
  only after the rules were frozen (commits `ae84496` and `2e0afab`).
- L2 was retrained on a separate labelled run, **train1** (22 variants at other rates, sources and
  ports; seed 1001; the OOD probe excluded).
- DEV and held-out are reported side by side and never averaged:
  [`dev_vs_heldout.md`](dev_vs_heldout.md), raw [`dev/results.json`](dev/results.json) and
  [`heldout/results.json`](heldout/results.json).

| | DEV (tuned on) | HELD-OUT run4 |
|---|---|---|
| Attacks detected | 10/10 | **10/10** |
| L3 named the attack (expected family) | 10/10 | **10/10** |
| Benign / flash crowd | clean / clean | **clean / clean** |
| L1 false positives (benign, flash crowd) | 0/413, 0/557 | **0/371, 0/322** |
| L2 attack detection (sampled flows) | 99.95% | **99.95%** |
| L2 macro-F1 (coarse families) | 0.872 | **0.800** |
| MTTD floods (first flagged flow after start) | 0.9–1.5 s | **1.2–1.4 s** |

Before v5.3.0 (same DEV runs):
- 3/6 attacks were fully detected, and L3 did not detect SYN, ACK or RST.
- L1 false-positived on 41% of flash-crowd flows.
- L2 caught 0/1,452 SYN flows.

**Held-out findings (as measured; nothing tuned on them):**
1. **L2 false positives on connection fragments before an attack.** The capture starts 1 s before
   the generator. It catches 2-packet TCP leftovers that the victim sends at the end of the previous
   scenario's connections. The retrained L2 labels these "ACK" (flood): 9 flows in the ICMP capture,
   3 in the low-and-slow capture ([`pre_start_check.json`](pre_start_check.json)).
   - That made the raw MTTD negative (ICMP −0.87 s, low-and-slow −0.94 s).
   - Counting only flows after the start: **ICMP 0.15 s, low-and-slow 118.1 s**.
   - Fix candidate for v5.4.0, using new DEV data: a minimum flow size / handshake context before
     an "ACK" class verdict.
2. **L2 per class on held-out:**
   - Syn, ACK, RST and LAND: about 1.00 F1.
   - UDP: 0.97 recall.
   - Slowloris: 0.50 recall. Reflection (NTP+DNS): 0.32. ICMP: 0.27 (only 50 ICMP training flows,
     because an ICMP flood is a handful of long flows).
   - Detection did not depend on these: L1 and the L3 rules named every held-out attack.
3. **The offline low-and-slow MTTD (118 s) is bound by flow completion.** Live, the same attack
   alerted at 18 s on DEV through the live slow-connection count. It was not measured live on run4.
4. **Some training scenarios fell short of their target rate:** `train_rst_a` reached 325 of 700
   pkt/s, and the training flash crowds 21–27 pkt/s (real HTTP connections).
5. **Caveat:** train1, DEV and run4 all come from the same generator and the same Mininet network.
   Configurations and seeds differ, but **lab numbers can still be inflated by generator bias**. They
   are not evidence for real-world traffic.

### Reproduce

```bash
# WSL2, as root (lab only)
sudo mn -c && sudo python3 -m lab.traffic.orchestrate --out data/lab_runs/run2 --containment

```

## Mock runner (`lab/runner.py`)

`MockRunner.run()` applies every check above. It then produces per-tick *descriptions* of the
traffic, with no packets, re-checking the kill switch before each tick. `to_aggregate()` turns a run
into a synthetic `IncidentAggregate` that can be replayed through L1 → L2 → rule-based L3.

`TestMockPipelineWiring` replays three scenarios and checks they land in their expected incident
family. **That is a wiring check, not detection evidence**: the aggregate is derived from the
scenario's own description. Measured MTTD, false positives and the coverage matrix need real lab
traffic (v4.6.1).
